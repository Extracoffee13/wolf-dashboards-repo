# First-Principles Spike — 2026-07-30

## Question

The `first-principles-backlog.md` file was empty, so this question was self-generated from current Construct work: this very repo runs a shared handoff log (`praxis-inbox.md`, appended to by independent agents on independent schedules via git commit/push, then presumably drained into `praxis-inbox-processed.md`). **From first principles — no existing distributed-systems documentation, no prior art lookup — how should a multi-agent system's shared append-only handoff log be structured to prevent lost updates, duplicate work, and stale reads?**

## First-principles answer (derived before any search)

Start from the primitives actually in play: several independent agent processes, each running on its own schedule, with no shared memory and no locks. Their only channel is a git-tracked flat file, mutated by read → append → commit → push. The question is what structural properties that channel needs so the system stays correct without coordination.

**1. The medium already gives you an atomicity primitive.** A git push against a branch either fast-forwards or is rejected outright — there is no partial-write state visible to other readers. That rejection-on-conflict behavior is structurally identical to a compare-and-swap: read a version, compute a new state, write it *conditioned on the version being unchanged*, and get a hard failure (not silent corruption) if someone else moved first. So the correctness of concurrent writers reduces to whether each writer *retries on rejection* — fetch, reapply its own diff, push again. Any writer that pushes once and gives up on rejection has a lost-update bug; the fix isn't a new mechanism, it's just closing the retry loop that the CAS-like primitive already demands.

**2. Minimize the conflict surface by construction.** If two agents both append new blocks to the end of the file, their diffs don't overlap textually and a rebase resolves automatically — no manual merge, no lost content. If instead agents ever *edit* existing blocks (e.g., to update a status field), two concurrent edits on the same block genuinely conflict and someone's write is silently at risk of being lost in manual conflict resolution. So the append-only discipline isn't a style preference, it's what makes the CAS retry in (1) actually resolve without human intervention almost all of the time.

**3. At-least-once delivery forces idempotent consumption.** Because a consumer reading the log can crash after reading but before finishing its side-effects (e.g., updating agent instructions from a lesson), and because the log can be re-read from scratch at any time, any given entry may be processed more than once. There is no way to prevent this without a distributed transaction across git and whatever the consumer mutates — not available here. So the only tractable path is to make re-processing harmless: give every entry a stable identity, and have the consumer check that identity against a durable "already handled" set before acting, then record it there. Without an explicit identity field, a consumer can only fall back to fragile proxies (full-block string match, position in file), which break the moment formatting drifts.

**4. Ordering should be assumed unnecessary unless proven otherwise.** Nothing in the structure guarantees a consumer reads the log at a moment when all concurrent writes have landed — different agents push on independent schedules, so "stale read" is the normal case, not an edge case. Trying to force strong consistency (locking, a single writer, a leader-election scheme) fights the medium for no benefit if the entries don't causally depend on each other. The cheaper and more robust move is to treat each entry as an independent, commutative fact: applying entries A-then-B or B-then-A leaves the same end state, and applying an entry an extra time is a no-op (from point 3). That combination — commutative, associative, idempotent — is exactly what lets a system converge correctly under any interleaving and any amount of re-delivery, without coordination.

**5. Putting it together**, the minimal correct structure is: (a) strictly append-only entries, never in-place edits; (b) each entry carries an explicit unique key — cheapest is `date + agent + task`, falling back to a running counter if that's not guaranteed unique; (c) a separate durable "processed" ledger recording consumed keys, so "unprocessed" is a plain set-difference the consumer can recompute safely on every run; (d) writers always retry-on-push-rejection rather than treating a rejected push as terminal.

Checking this against the repo as it stands: `praxis-inbox.md` already gets (a) right — the format is append-only fenced blocks. It does *not* yet get (b) or (c) right in an explicit, machine-checkable way: entries have `agent`/`task`/`date` fields but no single declared unique key, and `praxis-inbox-processed.md` exists as a file but currently holds no ID index — so a consumer today has no cheap, robust way to compute the set difference in point (c) without re-parsing and eyeballing full block contents.

## Corpus answer (searched after the derivation above)

The reasoning above maps almost exactly onto three named, well-established patterns:

- **Idempotent Consumer pattern** (microservices.io, and widely documented for Kafka/queue consumers): a message handler must produce the same outcome whether processed once or many times; the standard implementation is to assign every message a unique ID and have the consumer record processed IDs in durable storage, checking against that record before acting. The formula given in the corpus is explicit: *at-least-once delivery + idempotent consumer = effectively-exactly-once processing* — which is precisely the argument made in point (3) above.
- **CRDTs / commutative replicated data types** (Shapiro et al., 2007/2011): data structures designed so that concurrent, out-of-order, even repeated operations converge to the same state without coordination, by construction requiring operations to be commutative (and for idempotence, absorbing). This is the formal name for the "independent, commutative, idempotent fact" property invoked in point (4).
- **Optimistic Concurrency Control / compare-and-swap**: read a version, write conditioned on the version being unchanged, retry on rejection. The corpus explicitly notes this is the same mechanism underlying every database's optimistic locking, and that production systems must handle the rejection path with retry logic — exactly the "close the retry loop" argument in point (1).

None of these are exotic or contested; they are textbook-level distributed systems patterns, cited across microservices, database, and CRDT literature going back to the mid-2000s (OCC) and 2007-2011 (CRDTs).

## Delta category: **rediscovered**

The reasoning chain, built solely from the primitives of "independent writers, a git-backed append-only file, and periodic readers," landed on the same three mechanisms the corpus prescribes for this exact class of problem — idempotent-consumer identity+ledger, commutative/idempotent operation design (CRDT insight), and CAS-style optimistic concurrency with retry. This isn't a coincidence of vocabulary; the derivation reached the same *shape* of solution (unique key + durable processed-set + retry-on-conflict + append-only-by-construction) independently, which is the strongest form of validation available for a reasoning exercise — arriving at the standard answer without having read it.

## Commentary

The gap this spike actually surfaces isn't in the reasoning, it's in the implementation: `praxis-inbox.md` and `praxis-inbox-processed.md` exist but don't yet carry the explicit unique key or ID index that the (independently derived, and corpus-confirmed) idempotent-consumer pattern requires. That's a concrete, low-cost fix — add a `id:` field to each `PRAXIS_INBOX` block (e.g. `YYYY-MM-DD-agent-task`) and have whatever drains the inbox record consumed IDs in the processed file — worth flagging upstream even though it's outside this spike's scope to implement.
