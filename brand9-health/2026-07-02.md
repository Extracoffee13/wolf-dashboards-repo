# Brand 9 Site Health Check — 2026-07-02

## Overall status: 🔴 RED (audit blocked — not a confirmed site outage)

**Headline finding:** This session's outbound network policy blocks direct HTTPS access to `brand9signs.com`. The egress proxy returned `403` / "policy denial" on every attempt (WebFetch to the homepage, WebFetch to the category page, and a raw `curl`). Per the proxy's own guidance, blocked hosts are not to be retried or routed around — so none of the 6 planned checks could be executed against live site content this run. WebSearch (which does not go through this egress path) confirms the domain resolves and is indexed, so this is very likely a sandbox allowlist gap rather than evidence the site itself is down.

## Diagnostics performed

- `WebFetch https://brand9signs.com` → HTTP 403 Forbidden (from the request layer, before reaching WordPress)
- `WebFetch https://brand9signs.com/product-category/marketing-branding/` → HTTP 403 Forbidden
- `curl` (direct and through `$HTTPS_PROXY`) → `CONNECT tunnel failed, response 403`
- Proxy status endpoint (`/__agentproxy/status`) confirms: `"kind": "connect_rejected", "detail": "gateway answered 403 to CONNECT (policy denial or upstream failure)", "host": "brand9signs.com:443"`
- `WebSearch "brand9signs.com"` → succeeds, returns the live homepage title/snippet ("Brand 9 Signs | Homebuilder, Military & Development Signage"), confirming the domain is up and indexed as of this search. WebSearch does not traverse the blocked egress path, so it cannot substitute for the console-error, embed-rendering, Yoast-meta, or per-page-status checks this routine requires.

## Recommended action

Add `brand9signs.com` (and any WordPress admin/API host it uses) to this environment's outbound allowlist so future scheduled runs of this routine can actually reach the site. Until that's done, this check cannot produce a real GREEN/YELLOW/RED verdict on site content — it can only confirm the routine's own access is broken.
