## 2. A separate, more durable problem: the checklist targets a site that no longer exists

Independent of the network block, the repo's `b9-site-deploy` skill (verified 2026-08-08,
updated 2026-08-11) states plainly:

> brand9signs.com is a static HTML build on DreamHost, deployed by Hermes. It is **NOT
> WordPress**. Editing WordPress/wp-admin edits a dead legacy backend that no longer serves the
> live site (`/wp-json/` returns the static site's custom 404).

The live site is ~357 static pages, folder-per-slug (`/<slug>/index.html`), built around
city/vertical/homebuilder "answer pages" for a sign-fabrication business — not a WooCommerce
catalog. A `WebSearch site:brand9signs.com` this run returned pages like
`sign-company-orange-park-fl` and `jacksonville-sign-company`, consistent with that model, and
found nothing resembling a `/product-category/marketing-branding/` shop page.

This run's checklist (16-tile nav row + 8 product cards, a "Motion Films product page," Yoast
focus keyphrase / meta description / SEO title fields) describes the **pre-rebuild WordPress
site**. Per the deploy skill, that backend is dead and Yoast doesn't apply to the current static
build at all. Running these checks as written — even with network access — would likely report
false 404s/missing-content on a site that is actually healthy, or silently check nothing
meaningful.

Additionally, per the `b9-verify-and-index` skill, brand9signs.com sits behind an `sgcaptcha`
bot-shield that is known to make plain `curl`/server-side fetches **lie about page content**
(serve a challenge page instead of the real one) — the documented workaround is verification
through an authenticated browser session, not a headless fetch. That's a second reason a
`web_fetch`-only audit design can't be trusted here even once egress is allowed.
