# Brand 9 Signs — Site Health Report
**Date:** 2026-08-17
**Scope:** brand9signs.com daily automated health check
**Overall status: 🔴 RED — audit could not be executed**

## Summary

Today's scheduled check could not reach brand9signs.com at all, and the checklist
this routine was configured with is written against the wrong site architecture.
Neither problem is a signal that the live site is actually down — it means this
routine, as currently built, cannot produce a reliable health signal today.

## What happened

1. **Total network egress block.** Every attempt to reach `brand9signs.com` from
   this session failed before any content was returned:
   - `WebFetch` on `https://brand9signs.com` → `EGRESS_BLOCKED: Access to
     brand9signs.com is blocked by the network egress proxy.`
   - `WebFetch` on `https://brand9signs.com/product-category/marketing-branding/`
     → same `EGRESS_BLOCKED` error.
   - Direct `curl` to `https://brand9signs.com` → `curl: (56) CONNECT tunnel
     failed, response 403`.
   - No browser/computer-use tool (Claude-in-Chrome, Hermes desktop control) is
     available in this session to fall back on an authenticated-browser check.

   This is a sandbox/session network restriction, not evidence of a site outage.
   Per the `b9-verify-and-index` operating notes, brand9signs.com also sits
   behind an sgcaptcha bot-shield that returns a captcha redirect (not real
   content) to plain cloud `curl`/fetch even when egress isn't blocked — so even
   on a day egress is open, this checklist's step 1–5 fetches need to go through
   an authenticated browser session (Hermes/Claude-in-Chrome) to be trustworthy,
   not raw `web_fetch`.

2. **The checklist itself is written for the wrong site.** Steps 2–4 of this
   routine (a WooCommerce-style `/product-category/marketing-branding/` page
   with a 16-tile nav row, 8 product cards, individual product pages with
   prices, and Yoast SEO meta fields) describe a WordPress/WooCommerce site.
   Per the authoritative `b9-site-deploy` skill (verified 2026-08-08):
   > "brand9signs.com is a static HTML build on DreamHost, deployed by Hermes.
   > It is NOT WordPress... Never use the wordpress-yoast-publishing skill...
   > for B9 — [it describes] the pre-rebuild WordPress workflow and [is] stale."

   The live site is ~357 static pages, folder-per-slug (`/<slug>/index.html`),
   answer/case-study/commercial-intent pages — not a product catalog. A
   `WebSearch site:brand9signs.com` this run turned up only that pattern (e.g.
   `/sign-company-orange-park-fl/`, `/jacksonville-sign-company/`), consistent
   with the static build and inconsistent with a `/product-category/` /
   Yoast-driven store existing on the live domain.

## Recommendation

- Treat today's RED as **"audit not run,"** not **"site broken."**
- Fix the routine before next run:
  - Route the actual fetch/verify steps through an authenticated-browser path
    (Hermes desktop control or Claude-in-Chrome) instead of raw `web_fetch`,
    per `b9-verify-and-index` — plain cloud fetches are blocked or captcha'd.
  - Rewrite steps 2–4 to match the real site: static answer/case-study pages,
    no WooCommerce product catalog, no Yoast plugin. If a "Motion Films"
    product/feature page and a Marketing/Branding category page do exist on
    the live static build, confirm their real slugs and content model first
    (don't assume WordPress conventions) before re-checking them automatically.
- If this session's egress restriction to brand9signs.com is unexpected for a
  monitoring routine, confirm the environment's network policy allows the
  target domain, or delegate the check to a session/agent that has Hermes or
  Claude-in-Chrome access.
