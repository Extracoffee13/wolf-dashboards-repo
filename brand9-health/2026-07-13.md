## Root cause

Both the `WebFetch` tool and a raw `curl` (via the session's egress proxy)
returned HTTP 403 for `brand9signs.com` on every path, including
`robots.txt`, which is normally unrestricted even behind bot-protection
WAFs. The proxy status endpoint confirms this is a **policy-level CONNECT
rejection**, not a response from the site itself:

```
"kind": "connect_rejected",
"detail": "gateway answered 403 to CONNECT (policy denial or upstream failure)",
"host": "brand9signs.com:443"
```

Per the proxy's own guidance, this class of failure ("destination host not
allowed by your organization's egress policy for this session") should be
reported rather than retried or routed around, so no further fetch attempts
were made.

## Independent signal (Google index, via WebSearch)

A `site:brand9signs.com` search returned live, recently-indexed pages,
including `/product-category/marketing-branding/`, several `/product/...`
pages, and the homepage — with normal titles/snippets. This suggests the
site was reachable by Googlebot recently and is not obviously down, but it
does **not** confirm today's console-error, embed, price, or Yoast-meta
checks, none of which are visible from a search snippet.

## Action needed

This routine needs either (a) `brand9signs.com` added to the session's
egress allowlist, or (b) a different execution path (e.g. an
authenticated/allowed browsing tool) to actually perform the checks. Until
then, this daily check cannot confirm real site health — treat today's run
as **inconclusive**, not as a clean bill of health.
